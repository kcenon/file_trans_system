# Batch scheduling

The public `upload_files` and `download_files` APIs own every input path and its options. A scheduler advances each entry through pending → starting → running → terminal. Starting counts against the concurrency limit; completion events release a slot and wake the scheduler. No transfer ID stands for pending work.

`batch_options::max_concurrent` accepts 1–256, inclusive. Empty input or invalid concurrency is rejected before scheduling. Local path errors and server failures become individual results at their original input indices. With `continue_on_error = true`, remaining files continue. With it disabled, the first observed failure cancels active work and gives every pending entry an explicit “Skipped after batch error” result. Work already completed keeps its result.

Pause prevents new admission and pauses active handles. A chunk already being processed may finish before pause takes effect. Resume reactivates handles and scheduling. Cancellation covers active and pending entries; pending entries receive a failed “Batch cancelled” result with zero transferred bytes. Every input gets exactly one outcome.

Waits observe the scheduler without updating counters. A timeout leaves the batch running. Repeated successful waits return the same counts, bytes, per-file outcomes and elapsed duration. `get_individual_handles()` returns started handles in input order; unstarted entries have no handle. Per-file results always retain all inputs in order. Upload total size is known from local metadata; download progress reports the sum of sizes discovered so far, so its denominator can grow as pending downloads start. Result byte totals include partial bytes from failed/cancelled transfers.

Overwrite and compression overrides are preserved for both directions. Download success follows verified local commit and queuing the final protocol acknowledgement, so the next batch request follows it on the ordered connection. Client destruction cancels scheduling and joins every dynamically created transfer job. Application callbacks must not destroy the client from one of its own worker callbacks.

Validation: `PublicBatchTest.*` uses real TCP endpoints. Ten uploads and ten downloads at concurrency three verify all destination hashes and exact aggregate bytes; server admission observes no more than three active transfers. Additional cases cover initial/later path or admission errors, continue/fail-fast behavior, invalid concurrency, pause before slot release, cancellation, stable repeated waits, and shutdown with five simultaneous batches. `BatchTransferTest.*` retains component/type/invalid-handle tests; the former unchecked localhost:8080 assumptions were replaced with these real-server cases. The CI batch exclusion is removed.
